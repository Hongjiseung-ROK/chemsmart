# M4 — Defect-Driven Expansion

## Objective

Use opened M3 failures to expand ChemSmart only through unique, reproducible,
cross-domain hypotheses rather than paper-specific patches.

## Adaptive loop

Maintain a causal defect ledger with severity, frequency, stage, affected
papers, recoverability, oracle, and disposition. Prioritize false-ready,
molecular identity/electronic-state drift, unsupported settings, registry to
loader disagreement, knowledge-pack scope leakage, command-semantic failure,
preview failure, provenance mismatch, critic error, context/handoff loss, and
budget/repair failure.

For the highest-value unresolved defect, preregister one causal hypothesis,
one changed factor, comparator, expected observation, deterministic oracle,
source/prompt/tool/configuration/budget hashes, and novelty rationale. Run a
paired experiment, grade deterministically, obtain a fresh read-only
cross-examination, and retain, revise, or reject the change. A retained setting
record or knowledge rule must improve another chemistry domain before becoming
a development-default candidate. Record negative results and retire ineffective
hypotheses.

API calls have no predetermined count ceiling and continue only while unique,
verifiable hypotheses remain within current user-owned quota and the bounded
network envelope. Do not top up, bypass a failed provider, repeat identical
prompts, or call merely to consume quota. Stop on explicit quota exhaustion,
credential revocation, no runnable hypothesis, or any safety red line.

## Architectural rule

Fix capability in the lowest authoritative layer: loader/schema registry for
expressibility, domain pack for sourced applicability, compiler/validator for
deterministic semantics, and prompt/harness only for orchestration. Do not hide
a code or evidence defect inside persona text. Preserve K0 and the frozen M3
receipt so every claimed improvement remains comparable.

## Exit gate and claim boundary

Every adopted change has paired evidence, cross-domain confirmation,
deterministic replay/rerender, paper-level regressions, and zero approval,
native-input, artifact, secret, false-success, or terminal-event violations.
This phase may justify an implementation candidate and a transparent paper
draft with negative results. A SOTA claim requires a new external lockbox,
competitive baselines, preregistered metrics, statistical uncertainty, and
independent evidence; M3/M4 development outcomes alone cannot support it.
