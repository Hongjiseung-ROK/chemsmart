# P3 live DeepSeek capability specimen v2

## Status

Pre-call protocol frozen on 2026-08-01. This is a distinct, one-request
follow-up to the exhausted v1 specimen, not a retry or an edit to v1. It is
authorized only because the program's P1 receipt records an existing positive
DeepSeek allowance and the user authorized bounded API use within existing
quota. No request may occur until the offline contract test, dry run, and
credential-only preflight have each passed. The protocol closes after one
response or one preflight/provider failure, with no retry.

## Objective

Test one narrow hypothesis generated by the v1 failure: under the same
official endpoint, model, sanitized messages, fixed function schema, tool
selection, timeout, and non-execution boundary, does raising only the output
ceiling from 64 to 256 permit a structurally valid fixed function record? A
positive observation would establish only that narrow direct-endpoint fact. It
cannot establish normal ChemSmart provider or CLI behavior, tool execution,
chemical correctness, component benefit, held-out performance, replication,
training readiness, paper readiness, or SOTA.

## Inputs

| Input | Required use |
| --- | --- |
| P1 DeepSeek API receipt | Pin model, official-root digest, configured alias, redacted allowance, and prior observation time. It is not a current-balance claim. |
| Frozen P3 v1 blocked receipt | Require its `P3-F12` / blocked state and retain its SHA-256 in the v2 receipt. It supplies the failure evidence, not an excuse to retry v1. |
| Frozen v1 source/protocol | Use only for immutable comparison. The v2 request contract must differ only at `max_tokens`. |
| New v2 source and offline fixtures | Build, inspect, and structurally validate a separate response receipt without entering the active provider/tool-loop/CLI path. |

## Tools and authority

- Permitted: one direct official DeepSeek Chat-Completions SDK request from the
  isolated runner; deterministic offline tests; read-only P1/v1 receipt and
  source hashing; and sanitized local receipt validation.
- Prohibited: normal ChemSmart provider/tool-loop/CLI execution; function
  dispatch; chemistry-engine, scheduler, file, or network-tool use from the
  returned function; dependencies; configuration writes; balance top-ups;
  fresh account probes; publication; commits; and pushes.
- Credentials are resolved only in-process to the canonical alias from the
  P1-pinned configured alias and are removed in `finally`. Neither their
  values nor request headers, raw prompts, raw response text, function
  arguments, reasoning content, URLs, or error text may be persisted.

## Gates

| Gate | Green condition | Red condition |
| --- | --- | --- |
| V2-G1: immutable delta | Offline comparison proves the request contract equals v1 after replacing only `max_tokens`. | Any other request-surface, model, endpoint, tool, timing, cost, or execution drift. |
| V2-G2: budget and credential boundary | Dry run and credential-only preflight pass without a model call; fixed local estimate is within USD 0.005 and historic P1 allowance. | Missing/drifting P1/v1 input, unresolved alias, request-size/cost violation, or retained credential. |
| V2-G3: non-execution | Exactly zero tool executions, engines, schedulers, and follow-up requests. | Any dispatch or real execution. |
| V2-G4: structural observation | One response has the fixed returned model, `finish_reason=tool_calls`, exactly one named call, exact JSON arguments, no retained reasoning content, valid numeric usage, and cost/time within ceilings. | Any transport, provider, model, structure, schema, cost, time, or redaction defect. |
| V2-G5: claim discipline | The receipt is deterministic-valid and its result remains a narrow provider-surface observation. | Any promotion to active-agent, scientific, evaluation, paper, training, or SOTA claim. |

## Blockers

- P3 v1 is terminal and must not be rerun, edited, or reclassified.
- P1 allowance is historical and does not prove current available balance;
  this protocol permits no fresh usage probe and no charge beyond its fixed
  USD 0.005 ceiling.
- A completed v2 receipt cannot make P3-G2/P3-G3, P4 executor readiness,
  P5 ablation, P6 paper/training, or any SOTA claim green.
- Any preflight failure or red response is terminal for v2. A later study
  needs a separately frozen protocol, budget, and decision ledger.

## Phase-close validation

1. Run the v2 offline contract test once after source changes.
2. Run one no-request dry run and one no-request credential-only preflight.
3. If and only if both are green, perform the single allowed request once.
4. Persist a sanitized receipt, validate it once with a deterministic
   receipt checker, and run `git diff --check` once. Do not rerun v1, broad
   suites, or the v2 provider request.
